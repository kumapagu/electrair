# electrair プロトタイプ開発・検証計画／実装引継ぎ資料

作成日：2026年11月16日（日本時間）  
更新日：2026年11月19日（日本時間）  
版：0.7／AI用ドキュメント整備・仕様分割版  
対象：家庭用エアコン入替工事の社内業務アプリ  
本資料は次の実装担当への引継ぎ用。現時点では実装を開始しない。

開発工程と確認方法は[プロトタイプ開発フロー](development-workflow.md)を基準とする。人間は①作業の定義、②設計、⑧最終レビューをそれぞれ確認する。①と②はプロトタイプでも別々に行う。本資料内の従来の「開発前に詳細を具体化」「本人が最終確認」という記述には、この確認工程を適用する。今回の更新はフローの資料化までであり、個別作業の承認や実装を意味しない。

機能の完成に加え、仮説・利用者による検証・次に進む判断を中心に据える。0.5版では壁打ちで決定した初回範囲、個人単位の割当、時間・写真のルール、スマホ優先のデザイン、shadcn/ui＋Tailwind CSS、AI中心の開発・レビュー体制、検証順序を反映した。開発期間・期限は設定しない。Storybookや画面等の実装はまだ行っていない。

詳細仕様は[仕様一覧](specs/README.md)、デザインは[共通方針](design-guidelines.md)を正本とする。移行による業務要件の変更はない。

## 1. 目的と位置づけ

社長が行っている「日程・担当の調整」と「施工後の写真・報告の回収」を、少ない操作で行えるかをプロトタイプで検証する。

成果物は動く画面に加え、「採用する仕様」「修正する仕様」「まだ分からない点」「次へ進む判断」とする。最初は業務の流れと操作を検証し、その後に端末間共有を含む業務上の効果を検証する。

| 検証の目的 | 確かめること | 今回の扱い |
| --- | --- | --- |
| 課題・価値 | 現在の負担が減り、新しい入力負担に見合うか | 初回は見込みを整理。実際の効果は後続の試行で確認 |
| 業務 | 割当・変更・報告・確認が仕事に合うか | 最初の重点 |
| 操作 | 社長・作業員が迷わず進められるか | 最初の重点 |
| 技術 | 端末で写真操作や保存等が成立するか | 検証に必要な部分から実物に近づける |

まずは架空データで業務の流れと画面を確認する。実業務への導入、本番運用、外販用SaaSの開発は今回の範囲に含めない。資料内の仮置きはユーザーによる確定事項ではなく、実装を進めるための初期値である。

### 確認したいこと

- 社長が、未割当案件と各担当の予定を一緒に見て、日程・担当を決められるか。
- 作業員が、自分の案件から迷わず写真・作業内容を報告できるか。
- 社長が、報告を追いかける必要のある案件と、確認すればよい案件を区別できるか。
- 現在のLINEでの情報共有から移す価値があるか。入力の二度手間を増やさないか。

### 最初の検証仮説

以下は期待であり、効果が確認されたことを意味しない。

| ID | 仮説 | 操作課題 | 観察すること |
| --- | --- | --- | --- |
| H01 | 未割当と担当別予定を一緒に見れば、社長が割当・変更を判断しやすい | 未割当案件の割当、既存案件の日付・担当変更 | 完遂可否、支援回数、不足情報、所要時間 |
| H02 | 今日の案件から写真と最低限の情報を入力すれば、作業員が報告を終えられる | スマホで案件を開き、写真・結果を保存し提出 | 迷い、入力負担、写真分類、保存・提出の理解 |
| H03 | 未報告と確認待ちを区別できれば、社長が次の対応を把握しやすい | 催促が必要な案件と確認すべき報告の発見 | 誤認、見落とし、残るLINE等の作業 |

現在の手順も比較の基準として記録する。代表的な依頼と報告を匿名化して整理し、転記・確認・催促の手間や所要時間を確認する。最初から一律の目標時間を設けず、現在の運用と比較する。

- まず自社利用で磨き、将来のSaaS化を検討する。

## 3. プロトタイプの範囲

### 段階0：検証する課題と前提を揃える

development-workflow.mdに従い、開発計画と①作業の定義を用意して人間が確認し、その後に②設計を別途確認する。H01〜H03の操作課題、架空データ、観察記録を用意する。担当単位と基本の写真要件は決定事項に従い、移動時間の重要性や元請け別の追加要件は後続で確認する。未回答でも仮置きで着手できるが、検証結果に与える限界を記録する。必要に応じ簡単な画面で用語や配置を確認する。Figma等の特定ツールは必須としない。

### 段階1：主要な流れをつなぐ最小プロトタイプ

「案件を選ぶ → 日時・担当を決める → 作業員が案件を確認する → 写真と結果を提出する → 社長が確認する」を試せるようにする。

| 機能 | 最初に作る範囲 |
| --- | --- |
| 案件 | サンプル一覧・詳細。新規登録はサンプルで代替してよい |
| 予定・割当 | 未割当、担当別予定、日時・担当の設定・変更、重複検知 |
| 作業員 | 自分の今日の案件、現場情報・注意事項の確認 |
| 報告 | 1台分の施工前・施工後写真、作業結果「完了」、メモ、下書き保存・提出 |
| 管理者確認 | 未報告・確認待ちの区別、報告閲覧、確認済みへの変更 |
| 保存 | 再読込後の保持、架空データへのリセット |

開発中の機能確認・レビュー・修正は基本的にAIが進める。初回は合意した流れを一通り試せる状態にして依頼者本人が全体を最終確認し、修正後に社長・従業員による業務・操作検証を行う。途中のレビュー方法と区切りは開発計画を基に開発前に具体化する。

### 段階2：検証結果を根拠に追加する候補

案件登録・検索・絞込、複数台、施工チェック、追加部材・追加作業、再訪問結果、差し戻し・再提出を候補とする。すべてを初回の必須機能にせず、どの仮説や観察結果に対応するかを決めて追加する。

以下は段階2までに採用を検討する全体像であり、一括実装の要求ではない。

1. 案件の仮登録・編集・一覧・詳細。
2. 週の予定表示、担当別表示、未割当案件の表示。
3. 工事日時・担当の設定と変更、同じ担当の時間重複の警告。
4. 作業員別の今日の案件表示。
5. 機器ごとの写真追加・削除、施工チェック、作業メモ、追加部材・追加作業の記録。
6. 報告の下書き保存・提出。
7. 未報告・確認待ち・差し戻しの一覧、報告の確認・差し戻し・再提出。
8. 架空データへのリセット。

### 段階3：端末間共有を含む小規模な試行（今回の範囲外）

段階1〜2の結果から進むと判断した場合に、共有保存・必要な認証等を別途設計し、管理者・従業員それぞれのスマホやPCで情報がつながる状態を検証する。催促回数、報告漏れ、管理時間等は、現在の運用と比較できる期間・対象を決めて確認する。

### 今回は作らない機能

- メール・LINEの自動取り込み、実際の通知・送信。
- 元請け専用システムとの連携、指定帳票・PDFの出力。
- 自動割当、移動経路の最適化、資格条件による自動判定。
- 見積・請求・決済・会計・詳細な原価管理。
- 独立した機器台帳画面、保証・定期点検管理。
- 本番認証、会社間のデータ分離、課金・テナント管理。
- 本番用クラウド構築、オフライン同期、複数端末同期。

型番等の機器情報は案件内に残す。台帳画面は後続段階で検討する。LINEへの引継ぎは将来の候補であり、プロトタイプでは送信済みと誤認させる表示をしない。

## 9. 技術・保存についての引継ぎ

### 採用する技術とアプリ構成

| 項目 | 方針 | 位置づけ |
| --- | --- | --- |
| 言語 | TypeScript | 採用。案件・予定・報告等の型を共通に定義する |
| UI | React | 採用。管理者用・従業員用の両画面を作る |
| 開発・ビルド | Vite | 採用。ブラウザで動くWebプロトタイプを構築する |
| 部品の表示・状態確認 | Storybook | 採用。同じリポジトリ内で実アプリのReact部品を表示する |
| リポジトリ・アプリ | electrairの1リポジトリ・1つのWebアプリ | 採用。利用者や画面ごとにリポジトリを分けない |
| UI部品 | shadcn/ui | 採用。必要な部品をプロジェクト内に取り込み、共通デザインに調整する |
| スタイル | Tailwind CSS＋CSS変数 | 採用。色・文字・余白等の共通値を管理する |
| 初期の保存先 | IndexedDB | 案件情報・写真を同じブラウザ内に保存する |
| 認証 | 管理者・作業員の役割切替で代替 | 操作検証用。実際のアクセス制御は行わない |

管理者・従業員ともスマホを主要端末とし、iPhoneのSafariを優先して操作確認する。PCの表示にも対応する。利用者ごとのメニューと、画面幅に応じたレイアウトを用意する。案件・予定・報告のデータ、業務ロジック、共通UI部品は同じコードベースで共有する。画面間で案件データを別々に持たない。

### URL構成の例

以下は実装時の出発点であり、画面を独立ページにすることを強制しない。

| URL例 | 利用者 | 内容 |
| --- | --- | --- |
| `/admin/schedule` | 管理者 | 予定・担当の割当 |
| `/admin/reports` | 管理者 | 未報告の把握、報告確認 |
| `/worker/jobs` | 従業員 | 今日の案件 |
| `/worker/jobs/:id` | 従業員 | 現場情報、写真・作業報告 |

URLの分離と役割切替は、本番の権限管理を保証しない。ルーティング用ライブラリ等の補助技術は実装時に選び、起動・ビルドに必要な依存関係とバージョンを記録する。

### 実装時に決めること・後続段階で検討すること

- 着手時に実行環境を確認し、Node.js等のバージョン・パッケージ管理方法・依存関係を決め、起動・ビルド・型確認の手順を残す。
- TypeScriptの型確認に加え、入力値の検証と主要な操作の動作確認を行う。
- 保存処理は画面から呼び出す共通処理にまとめ、将来の共有保存への変更時に見直しやすくする。初回から汎用的な基盤を作り込まない。
- スマホで確認する際のアクセス方法を起動手順に記載する。同じアプリをPCとスマホで開いても、ブラウザ内のデータは共有されないため、各端末でサンプルを用意する。
- 段階3で端末間共有を試す場合は、API・共有データベース・写真の保存先・ログインと権限管理を検討する。Next.js等への変更を前提条件にはしない。
- 検証に必要な操作を優先し、プロトタイプのためだけに本番インフラを構築しない。

## 10. 完成条件・確認シナリオ

### 機能が正しく動くかの確認

P01〜P14の定義と段階別の適用範囲は[完成条件・確認シナリオ](specs/acceptance.md)を参照する。以下は利用者による検証を扱う。

### 利用者による検証の方法

初回は依頼者本人が管理者・従業員の両役割を操作し、全体を確認する。AIが行うレビュー・動作確認と、依頼者の最終確認を分けて記録する。修正後に実際の社長・従業員による検証へ進む。後続の参加人数・日程は必要になった段階で決める。

依頼者のみの確認でH01〜H03の実利用者への有効性が確認されたとは扱わない。少人数の利用者検証も全利用者への有効性を断定しない。以下は主に後続の利用者検証の手順であり、初回確認でも操作課題と記録方法を活用できる。

1. 現在の手順と比較の基準を確認する。
2. 架空データを戻し、同じ条件で操作課題を伝える。
3. ボタン名や手順は先に説明せず、「明日のこの案件を田中さんに割り当ててください」等、目的を伝える。
4. 止まった場所、探した情報、誤操作、支援した時点と内容を記録する。
5. 終了後に迷った理由、必要情報、現在より増減する手間を聞く。
6. 重要な問題を修正し、同じ課題で再検証する。

iPhoneのSafariで、管理者の日程・担当変更と報告確認、従業員の写真選択・追加・保存・提出まで実機確認する。PC上の表示幅変更による確認と実機操作を分け、端末・OS・ブラウザ・写真形式を記録する。対応外形式が使われていた場合は後続の技術検証項目にする。

### 観察記録のテンプレート

| 実施日・版 | 利用者・端末 | 仮説／課題 | 完遂・支援・時間 | 観察事実／発言 | 解釈・原因の仮説 | 修正案・優先度 | 再検証結果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 未実施 | — | — | — | — | — | — | — |

事実と解釈を分ける。「使いにくい」という感想だけで終えず、どの操作で何が起きたかを残す。

### 次へ進む判断基準（初期案）

初回の区切りは、AIによる確認・修正後、依頼者本人が合意した範囲の画面と動作を確認して採否を判断できる状態とする。以下のH01〜H03は、主にその後の実利用者による検証で判断する。未実施の利用者検証を初回実装の完了条件にしない。

| 対象 | 次へ進む目安 | 修正・再検証する例 |
| --- | --- | --- |
| H01 | 社長が手順の支援なしに割当・変更を完遂し、判断に必要な情報を得られる | 移動や担当者情報の不足で判断できない |
| H02 | 参加した作業員が実機で報告まで完遂し、管理側が必要情報を確認できる | 写真の分類で迷う、必須入力が多く報告が止まる |
| H03 | 社長が未報告と確認待ちを正しく区別し、次の対応を説明できる | 確認済みを元請け報告済みと誤認する、対象を見落とす |
| 運用全体 | 減る手間・増える手間・残るLINE等の作業を具体的に説明できる | 二重入力が増え、解消の見込みが立たない |

各回の終了時に「次の段階へ進む／修正して再検証／仮説や対象範囲を見直す」を記録する。操作を完遂しても、必要情報や業務上の課題が残れば成功と断定しない。

同一ブラウザの役割切替で確認できるのは画面・操作・状態のつながりである。複数人への伝達、日程変更の認知、実際の催促削減、複数端末の同期は確認できない。これらは段階3で検証する。

## 11. 実装の順序

1. 開発フローに従い、AIが開発計画と①作業の定義を用意し、人間が目的・範囲・完成条件を承認する。次にAIが②設計と代表画面を用意し、人間が業務ルール・画面・操作の方向性を別途承認する。今回の資料更新では個別作業の承認や実装は開始しない。
2. H01〜H03の操作課題、前提、記録を用意し、共通デザインルールとStorybookの最小環境を整える。
3. AIがサンプル・保存・予定と割当を実装し、機能確認・レビュー・修正を進める。
4. AIが今日の案件・写真・下書き・提出・管理側確認をつなぎ、合意した範囲の動作と画面を確認する。
5. AIが確認結果・制限・未確認事項を整理し、依頼者本人が全体を最終確認して採否を判断する。必要な修正をAIが行う。
6. 修正後に社長・従業員がH01〜H03を検証し、観察結果から段階2の追加範囲や段階3の検討を判断する。

開発期間・期限は設定しない。日数で区切らず、合意した範囲が動き、依頼者が確認できる状態を区切りとする。詳細フローはdevelopment-workflow.mdに従い、個別の計画・確認項目は着手時に具体化する。範囲を無制限に広げない。

AIが補った仕様も仮置きとして記録し、変更理由を仮説・観察結果と結び付ける。画面・用語・業務ルールの学びを残し、本番でのコード再利用、認証・保存・同期の仕組みは検証後に見直す。

実装成果物には起動方法、実装範囲、仮置き一覧、保存範囲と制限、機能確認結果、利用者の観察記録、採用・修正・保留の判断を含める。未実施の検証は結果として記載せず、業務上の効果は検証前に断定しない。

## 12. 優先して確認する前提・後続事項

初回の担当単位、時間指定、写真要件は第2節の決定事項に従う。以下のうち、割当判断に必要な追加情報や実際の撮影・報告手順は、業務に影響するため後続の利用者検証で確認する。未回答でも仮置きで初回の実装・本人確認を進め、未確認のため判断できないことを明記する。観察で重大と判明したものは優先度を上げる。

- 実際の人数。初回は個人1名の割当で進め、チームや複数人割当の必要性は後続で確認する。
- 1日あたりの件数、標準所要時間、移動・休憩・休日の扱い。
- 元請け別の依頼形式、写真・チェック・報告書の指定。
- 現場での追加費用の承認方法、お客様と元請けのどちらが精算するか。
- 日程変更・キャンセル・再訪問が発生する頻度と引継ぎ方法。
- 誰が報告を確認し、誰が元請けへ報告するか。
- 現場の端末・通信環境、HEIC写真や圏外対応の必要性。
- 写真の保存期間、閲覧範囲、本番のバックアップ・復旧・認証要件。

デザイン管理とStorybookの運用は[移行先の資料](design-guidelines.md)を参照する。既存の段階1・段階2の区分を維持し、詳細は参照先を正本として管理する。

## 14. 決定事項と開発前に具体化する事項

主な方針は決定済み。細かな数値・補助技術・確認方法はAIが初期案を作り、決定済みの開発フローに沿って個別の計画・作業定義・設計を具体化する。「未決定」は必ずしも着手を止める事項ではない。

| 項目 | 現在の状態 | 内容・次の扱い |
| --- | --- | --- |
| 目的・仮説 | 初期案あり | H01〜H03。初回の本人確認と後続の実利用者検証を分ける |
| 初回の範囲 | 決定済み | サンプル案件の割当→案件確認・写真報告→管理者確認 |
| 後続の機能 | 決定済み | 新規案件登録・複数台・差し戻し・再訪問は初回に含めない |
| 担当・時間 | 決定済み | 1案件に作業員1名。日付・開始・終了時刻を指定 |
| 写真・機器情報 | 決定済み | 施工前後各1枚以上必須、その他写真と型番・製造番号は任意 |
| 利用端末 | 方針決定済み | 両役割でスマホ優先、基本はiPhone。Safariで確認し、PCも対応。機種・OS等は確認時に記録 |
| 技術・構成 | 決定済み | TypeScript・React・Vite、1リポジトリ・1Webアプリ、Storybook |
| UI部品・CSS | 決定済み | shadcn/ui＋Tailwind CSS。共通値はCSS変数で管理 |
| デザイン | 方向性決定済み | 白・薄いグレー＋青。大きめの文字・ボタン、色と文字による状態表示 |
| 色コード・寸法等 | 開発時に具体化 | AIが初期案を作り、代表画面と最終確認で調整 |
| 保存・認証 | 初期方針あり | IndexedDB、架空データ、役割切替。端末間共有は後続 |
| 画面・導線 | 初期案あり | 予定・割当と作業・報告から作る。スマホ管理操作を省略しない |
| Storybook | 方針決定済み | design-guidelines.mdの5種類から登録。全画面・全部品登録は要求しない |
| 開発環境・補助ライブラリ | 開発前に具体化 | AIが環境と依存関係を選定し、起動・型確認・ビルド方法を記録 |
| 開発・レビュー体制 | 決定済み | AIが設計案・テスト・開発・レビュー・修正。本人が①作業の定義、②設計、⑧最終レビューを別々に確認 |
| 開発計画・詳細フロー | フロー決定・個別計画は未作成 | development-workflow.mdに工程・確認条件を定義。着手時に個別の計画・作業定義・設計を用意 |
| 検証の順序 | 決定済み | 初回は本人の全体確認→修正→社長・従業員による検証 |
| 後続の検証参加者・日程 | 後で調整 | 実際の社長・従業員に試してもらう段階で決める |
| 開発期間・期限 | 設定しないと決定 | 合意した範囲が動き、本人が確認できる状態を区切りとする |
| 完成・次へ進む条件 | 初期案あり | 第10節の機能確認と本人最終確認。H01〜H03の実利用者検証は後続 |
| 業務の追加要件 | 後続確認 | 実人数、移動等の判断材料、元請け指定、通信・写真形式等 |
| 本番技術・外部連携 | 後回し | 共有DB・本番認証・LINE連携・SaaS化等は検証結果から検討 |

次の作業は、この資料とdevelopment-workflow.mdを基にした個別の開発計画・作業定義の作成と、①の人間確認とする。今回の依頼は資料への反映までであり、計画作成や実装には着手しない。期間の決定や実利用者の日程確保を着手条件にしない。追加の業務要件が判明した場合は、初回の決定事項と後続候補を区別して見直す。

## 15. 実装担当への依頼文

技術構成はTypeScript・React・Vite、UIはshadcn/ui＋Tailwind CSSとし、electrairの1リポジトリ・1つのWebアプリ内で管理者用と従業員用の画面を分ける。案件・予定・報告のデータと処理を共有し、初期の保存はIndexedDBを使う。Storybookも同じリポジトリに導入し、代表画面で使用する共通部品から登録する。全画面・全部品の登録は初回の完成条件にしない。技術は第9節、デザイン管理は[共通方針](design-guidelines.md)、着手前の整理事項は第14節に従う。

> この資料に基づき、家庭用エアコン入替工事のプロトタイプを段階的に作成してください。最初はH01〜H03の検証を目的とし、段階1の割当から報告確認までを最小限の機能でつないでください。開発・レビュー・修正は基本的にAIが進め、初回は依頼者本人の最終確認と修正後に社長・従業員の検証を行ってください。AIの確認・本人確認・実利用者検証は分けて記録してください。1案件につき作業員1名、工事日・開始終了時刻、施工前後各1枚以上の写真を初回の基準としてください。管理者・従業員の両方でiPhoneのSafariを優先し、PCにも対応してください。development-workflow.mdに従い、①作業の定義と②設計の人間確認を別々に行い、承認後に本格的な機能実装へ進めてください。開発期間・期限は設定しないでください。未確認の追加要件は仮置きで進め、未確認事項として残してください。複数台・施工チェック・追加内容・差し戻し・再訪問は初回の必須機能にせず、段階2への追加は観察結果から判断してください。架空データと同一ブラウザ内保存を使い、実認証・LINE連携・本番インフラ・請求は対象外とします。検証していない業務効果は断定せず、次に進む判断と未確認事項を添えて引き継いでください。
