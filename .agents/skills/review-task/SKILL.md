# review-task

プロジェクトルートを基準にパスを解決し、AGENTS.md、docs/development-workflow.md、docs/tasks/README.md、対象作業記録を読む。手順から仕様や承認を新設・上書きしない。結果は対象作業記録へ残す。

## 手順

1. 開発ルール・工程、セキュリティ・データ保護、仕様・実装、テストの網羅性を、4人のレビュワーエージェントに1観点ずつ依頼する。別セッションで並行実施し、同時実行数に制限があれば担当を分けたまま複数回に分ける。
2. 各セッションはモデル `gpt-6.2-sol`、推論設定 `high`、会話履歴の引継ぎなしで開始する。`spawn_agent` を使う場合は `model: "gpt-6.2-sol"`、`reasoning_effort: "high"`、`fork_turns: "none"` を指定する。各レビュワーに渡すのは担当、同じ対象コミットと比較元、承認済み仕様、作業記録と③の承認、採用済みADR、差分・テスト・検証結果への参照。実装者の所見と他のレビュワーの初回指摘は渡さない。
3. 各担当は開発フロー第8節に従って独立に確認し、必要な検証を行う。テストの網羅性担当は③の期待結果と実際のテストコードを照合し、抜けているケースや不具合を見逃す期待値・検証を指摘する。対応する仕様、抜け、見逃しうる不具合を添える。
4. 各指摘に根拠、再現条件、影響、対象箇所を添え、修正必須／改善候補／要判断に分類する。担当AIが提出後に重複をまとめて、修正必須を修正し、該当のレビュワーに修正版の再確認を依頼する。修正結果と影響範囲を記録する。
5. 修正必須の解消、ADRと実装の整合、確認結果の正確さを確かめて⑦へ渡す。人間の判断が必要な変更は開発フロー第9節に従う。
6. 独立セッションを使えない場合は、該当の観点を自己レビューまたは未実施とし、理由を最終確認資料に残す。
7. PRを作成する場合は、⑥のレビュー対象コミット・比較元・結果と作業記録へのリンクをPR本文に記載する。PR上でのエージェントレビュー依頼は行わない。差分が変わった場合の再確認は⑥で行う。

成果物はレビュー方法・対象版・指摘一覧・修正と再検証結果・残課題とする。
