# 初回プロトタイプ設計案 v0.1

- 更新日 2026年11月20日（日本時間）
- 状態 ②承認済み（推奨案を採用）
- 対象 [T002の承認済み作業定義](../tasks/T002-prototype.md#作業定義)

## 設計確認の判断点

- 管理者が「未割当案件」と「担当別の予定」から日程・担当を決められるか。工事時間、担当、訪問先を見て割当を判断できるか。
- 作業員が現場情報を確認してから写真を区分ごとに追加できるか。「下書き保存」と「報告を提出」の違い、必須写真が不足した場合の次の操作が伝わるか。
- 報告を出した後の日程・担当は閲覧のみとし、報告前の担当変更では案件の下書きを新しい担当へ引き継ぐ案でよいか。管理者の「確認済み」は社内確認として扱う。

### 提出後の日程・担当変更

| 案 | 操作と影響 |
| --- | --- |
| **提出後は閲覧のみ（推奨）** | 未提出の間は日時・担当を変更できる。提出後は割当と報告が同じ工事を指し続ける。訂正や再調整が必要になる場面は利用者検証で確認する |
| 提出後も変更できる | 訂正や担当変更に対応できる。提出時点の担当・日時と現在の予定を区別して保持し、一覧の分類、作業員の閲覧範囲、再確認の要否を追加で設計する必要がある |

推奨案では、未提出の下書きは案件に残す。担当変更時に「保存済みの下書きあり」を管理者に示し、変更後は新担当が引き継いで編集できる。元担当の作業員一覧からは外れる。下書きは案件内の同じ機器に対する作業記録として扱う。

疑似役割切替では管理者と作業員を切り替え、作業員を選ぶ。管理者メニューの「予定・割当」「報告確認」と作業員の「今日の案件」を入口にする。画面IDは[共通仕様](overview.md)を参照。ページ数とURL分割は使いやすさに応じて決める。

### 代表画面で試す操作

1. **予定・割当**で「青葉コーポ 201」の日時・担当を設定する。初期値の田中さん9:00–11:00は重複する。開始・終了を11:00–13:00に変えるか、空いている担当者に変えると、画面上の予定に反映する。日付選択と既存案件の「日程・担当を変更」も試せる。
2. **作業・報告**で固定の見本案件「若葉レジデンス 302」を開き、「報告を提出」を押して不足を確認する。施工前と施工後の見本を追加し、「工事が完了した」を選び、メモの入力、下書き保存、提出を試す。

②で提示した見本は2026年11月20日を「今日」に固定し、変更を画面内のメモリに保持した。実装版の操作手順と検証結果は[作業記録](../tasks/T002-prototype.md)を参照。

## 業務ルールと状態

| 操作 | 条件と成功時の状態 | 入力不足・失敗時 |
| --- | --- | --- |
| 割当・変更 | 現場住所、JSTの工事日、開始・終了、担当1名が揃い、同一担当・同日で他案件と重複しない場合に保存。工事が予定済み。既存案件の編集中は自案件を重複判定から外す | 不足と日時エラーを該当欄に表示。重複は相手の案件名・時間を表示し、フォームを保持する |
| 下書き保存 | 写真や結果が揃う前でも、用意した入力と写真を保存できる。報告は未提出 | 保存できなかった理由と再試行を示し、入力を保持する |
| 報告提出 | 担当作業員の未提出案件で、結果「完了」と施工前後各1枚以上が必要。保存完了後、工事は完了、報告は確認待ち。作業員画面は閲覧表示に切り替える | 不足する機器・写真区分・作業結果を示す。永続化に失敗したときは未提出のままにし、入力を保持する |
| 確認済みにする | 管理者の確認待ち報告を対象とする。確認の保存後に報告を確認済みにする | 失敗時は確認待ちのままにし、詳細を開いた状態で理由と再試行を示す |
| 初期サンプルに戻す | 削除の対象を説明する確認を挟み、確定した場合にリセット。実行日のJSTを基準にサンプルを再生成する案 | 取消時は現状を保持。書込み失敗時も既存データを維持し、理由を示す |

同日内の工事を扱い、開始と終了の間に重なりがある場合に重複とする。前件の終了と次件の開始が同時刻なら連続枠として保存できる。未報告はJSTの予定終了を**過ぎた**未提出案件から抽出する表示で、下書きを含む。提出済みは確認待ちまたは確認済みの一覧に出る。詳細は[予定・割当](scheduling.md)・[案件確認・報告](reporting.md)を参照。

処理中は同じ保存・提出・確認操作の連打を防ぐ。成功表示と一覧の更新は書込み完了後に行う。画像選択時はJPEG／PNG／WebPを受け付け、見本からの実装案では上限を1枚10MB（10,000,000バイト）、1機器につき全区分で合計10枚とする。対象外の画像形式と容量・枚数超過は、写真欄に理由を表示する。実機で形式や容量に起因する支障が出た場合は、観察結果を基に対応を検討する。[保存・復元](storage.md)

## データと画面部品

| データ | 初回の扱い |
| --- | --- |
| 案件・予定 | 案件IDが基準。元請け、訪問先、住所、依頼内容と注意事項、機器、任意の予定を関連づける。予定はJST日付、時刻、担当ID。未割当と担当・日付別一覧は同じデータから算出 |
| 機器・報告 | 1案件1台・報告は案件ごとに1件。機器情報、メモ、結果、提出・確認日時を保持。工事状態は予定と提出結果から、報告状態は提出・確認日時から算出する案 |
| 写真 | 写真ID、案件・機器との対応、区分、画像Blobを保持。案件情報と写真を共通保存処理が扱い、下書き保存・提出・リセットは一貫した単位で書き込む |
| 初期データ | 架空の管理者1名・作業員4名・元請け2社・案件6件を仮置き。未割当2、予定済み1、終了後の未提出1、確認待ち1、確認済み1で主要シナリオを再現。日付は初期化時のJSTから相対生成 |

画面は割当・案件・報告の機能ごとに分ける。重複・提出可否・状態の判定を画面から切り出し、読込と書込みを共通保存処理にまとめる。IndexedDBの書込みは関連データを同じトランザクションで処理し、読取りから検証・更新までをまとめる。再読込時は保存済みのデータで画面を復元する。[保存と役割切替のADR案](../adr/0001-local-storage-and-role-preview.md)

白・薄いグレーを背景に、主操作は青。基本の文字とフォーム入力は16pxを目安にし、主なボタンと入力欄は高さ44px以上。工事・報告を別の文字ラベルで表示し、入力エラーは本文と該当欄で識別できるようにする。同じ部品・トークンを実画面とStorybookで使う。[デザイン方針](../design-guidelines.md)・[表示トークンの見本](../../src/styles/tokens.css)
