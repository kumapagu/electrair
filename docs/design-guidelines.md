# デザイン・共通部品の方針

更新日：2026年11月24日（日本時間）

既存の実装引継ぎ資料0.6版からの整理。今回の移行は仕様変更・個別作業の承認を意味しない。段階2の候補は採用決定まで初回の実装対象に含めない。

### 表示上の方針

- 日本語UI。管理者・従業員の両画面でスマホ操作を優先し、基本はiPhoneのSafariで確認する。PCでも利用可能にする。
- 白・薄いグレーを基本に、青をメインカラーとする。文字・ボタンはスマホで読みやすく押しやすい大きさにする。具体的な色コード・寸法はAIが初期案を用意する。
- 管理者の予定はスマホでは日別カード、PCでは担当別・週別の一覧を基本案とする。スマホでも日程・担当変更と報告確認まで完結できるようにする。
- 工事状況と報告状況は別々のラベルで表示する。
- 色だけで状態を伝えず、文字を併記する。
- 未登録・空一覧・保存失敗・入力不足の表示を用意する。
- ダミーのボタンを置かない。対象外機能は操作できるように見せない。

## デザイン管理とStorybook

### 基準と管理する場所

レビューして採用したReactの実装を現在のデザインの基準にする。画面を生成AIで作成する場合も、共通ルールと既存部品を先に確認し、新しい色・部品を追加する理由を記録する。Figma等は必須としない。

以下はデザイン管理の配置。採用済みの初回プロトタイプ v0.1.0 の画面と、実アプリの共通部品を使ったStorybookを参照できる。[起動手順](README.md#開発確認環境)

| 場所 | 管理するもの |
| --- | --- |
| `docs/design-guidelines.md` | デザイン方針、用語、状態・操作・エラー表示の共通ルール |
| `src/styles/tokens.css` | 色・文字・余白・角丸等の共通値をCSS変数で定義 |
| `src/components/ui/` | ボタン・入力欄等の共通部品 |
| 部品に隣接する `*.stories.tsx` | 実アプリと同じ部品の表示例・状態別の例 |
| `src/features/` | 予定・案件・報告等の画面と処理 |
| `.storybook/` | Storybookの設定。共通スタイルを読み込む |
| Pull Requestまたは変更記録 | 変更目的、変更前後の画像、確認結果、採用理由 |
| [引継ぎ資料](prototype-handoff.md)・[仕様一覧](specs/README.md) | 目的・範囲・業務仕様への参照 |

仕様を複数資料に重複して詳述しない。スクリーンショットは変更前後の比較に使い、表示の基準は採用済みのコードとする。Storybook用に本体と異なる見た目の部品を複製しない。

### 開発・レビューの流れ

1. 管理者・従業員の両方でスマホ操作を優先する。白・薄いグレーと青の方針に沿い、AIが具体的な色・文字・余白・角丸の初期案を用意する。状態は色と文字を併用し、保存・提出・確認の用語を揃える。
2. React・ViteとStorybookの最小環境を同じリポジトリに用意する。Storybookは開発時の部品確認用とし、利用者向けメニューには含めない。
3. ①作業の定義の承認後、②設計の確認用に必要な基礎部品と代表画面「予定・割当」「作業・報告」を作る。iPhoneを優先してPC表示も確認し、人間が設計を承認してから本格的な機能実装へ進む。サンプルデータや未接続の処理は明示する。
4. 代表画面で使用した共通部品を整理し、Storybookに状態別の例を登録する。最初からすべてを汎用部品にしない。
5. 機能単位で変更目的を決め、ブランチで実装し、動く画面とStorybookをレビューする。通常・空状態・入力エラー・処理中等、変更に関係する状態を確認する。
6. 初回はAIによるレビュー・修正後、依頼者本人が全体を最終確認する。修正後に社長・従業員のH01〜H03の検証を行い、見た目の好みと業務・操作上の問題を分けて記録する。
7. 採用する変更を反映し、共通ルール・共通値・部品・Storyを必要に応じ同じ変更で更新する。変更理由を検証結果と結び付ける。

管理者と従業員で基礎部品を共有しつつ、スマホとPCのレイアウトは用途に合わせる。開発・レビュー・修正は基本的にAIが担当する。依頼者本人が確認する工程と判断条件は[開発フロー](development-workflow.md)に従う。変更記録と未確認事項を残す。

### 初期のStorybook登録対象

| 部品 | 確認する状態 |
| --- | --- |
| ボタン | 通常・無効・処理中 |
| 入力欄 | 通常・入力エラー |
| 状態ラベル | 未報告・確認待ち・確認済み。工事と報告の状態を区別する |
| 案件カード | 未割当・予定済み |
| 写真追加欄 | 写真なし・追加済み・エラー |

これらを初期の優先対象とし、画面実装に合わせて登録する。Storybookの起動・ビルド手順を記録し、登録した例が表示できることを確認する。全画面・全部品の登録、大規模なデザインシステム、網羅的な画像比較テストは初回の完成条件にしない。

Storybookでは部品の見た目と状態を確認する。実アプリでは割当から報告確認までの操作、保存、状態の連動を検証する。写真の実機操作・実際の保存はアプリ側で確認し、Storybookのサンプル表示だけで検証済みとしない。
