## 作業定義

### 目的と利用者

家庭用エアコン入替工事で、管理者（社長）が行う日程・担当の調整と報告回収、作業員が行う現場情報の確認と写真報告を、架空案件で一通り試せるようにする。管理者・作業員ともiPhone Safariでの操作を優先し、PCにも対応する。同一ブラウザで役割を切り替え、割当・写真・報告状態を引き継いで操作する。[引継ぎ資料の目的と仮説](../prototype-handoff.md#1-目的と位置づけ)

| 仮説 | 依頼者が試す操作 | 観察すること |
| --- | --- | --- |
| H01 割当・変更 | 未割当案件と担当別の予定を見て、工事日時と担当を決める。既存案件の工事日や担当も変更する | 空き枠を見つけられるか、判断に不足する情報があるか |
| H02 写真報告 | 担当作業員として今日の案件を開き、現場情報を確認し、施工前後の写真と作業結果を保存・提出する | 写真の分類で迷う箇所、入力の手間、下書きと提出の違いが伝わるか |
| H03 報告確認 | 管理者として未報告と確認待ちを探し、提出された写真・報告を確認済みにする | 催促が必要な案件と確認する報告を判別し、次の対応を説明できるか |

依頼者は⑧で両役割を操作し、採否を判断する。社長・作業員によるH01〜H03の実利用者検証は、その確認と修正の後に行う。現在の手順と比べた手間や残るLINE作業の観察は、その利用者検証で扱う。[利用者検証の手順](../prototype-handoff.md#10-完成条件確認シナリオ)

### 対象範囲

| 利用者・機能 | 段階1でできること |
| --- | --- |
| 管理者の予定・割当 | サンプル案件の一覧・詳細と担当別予定を見て、工事日・開始・終了時刻と担当作業員1名を設定・変更する。同じ担当の時間重複を確認する |
| 作業員の案件確認・報告 | 担当する今日の案件、現場情報・注意事項を確認する。1案件1台の写真、作業結果「完了」とメモを入力し、下書き保存・提出する。施工前と施工後の写真は各1枚以上、その他写真・型番・製造番号は任意 |
| 管理者の報告確認 | 未報告・確認待ち・確認済みを区別し、確認待ちの報告と写真を閲覧して確認済みにする |
| 共通の操作 | サンプルデータを使い疑似的に役割を切り替える。再読込後も同じブラウザで変更・写真を復元し、確認を経て初期サンプルに戻せる |

- 後続の候補は、新規案件登録・検索・絞込、複数台の報告、複数人の割当、施工チェック、追加作業・部材、差し戻し・再提出、再訪問。今回の対象外とする。
- 実認証、実顧客データ、端末間同期、LINE・メール取り込みや通知・外部送信、元請け向け帳票、請求、自動割当や移動時間等の自動判定、本番インフラは今回の対象外。[範囲と後続候補の詳細](../prototype-handoff.md#3-プロトタイプの範囲)

### 完成条件

同一ブラウザで、未割当案件の割当・変更から報告の確認済みまで通しで操作できることを確認する。個別条件は次表で確認し、詳しい仕様とP番号の定義は既存資料を参照する。[P01〜P14の正本](../specs/acceptance.md)

| ID | 段階1で試す操作 | 合格となる結果 |
| --- | --- | --- |
| P01 | 未割当案件に日時・担当を設定する | 未割当一覧から外れ、担当者の該当日に表示される |
| P02 | 同じ担当で重なる時間に別案件を割り当てる。次の開始を前の終了と同時刻にして試す | 重複時は該当案件名を表示して保存を止める。境界が接するだけなら重複として扱わない |
| P03 | 割当済み案件の日付や担当を変更する | 元の予定枠から外れ、変更先の枠と作業員の案件一覧に反映される |
| P04 | 作業員を切り替え、今日の案件を開く | 選んだ作業員の案件だけが表示され、現場情報を確認できる |
| P05 | 写真・メモを下書き保存して再読込する | 写真と入力が復元され、報告は未提出のままになる |
| P06（1台） | 施工前または施工後の写真が不足した状態で提出し、下書き保存も試す | 不足する機器・写真区分が表示され、提出を止める。下書きは保存できる |
| P06（複数台） | 対象外（複数台を段階2で採用した場合に確認） | — |
| P07 | 必須写真と作業結果「完了」を揃え、任意項目を空欄にして提出する | 工事は完了、報告は確認待ちとなり、管理者の一覧に表示される。作業員の編集が止まる |
| P08 | 対象外（差し戻し・再提出を段階2で採用した場合に確認） | — |
| P09 | 管理者が確認待ちの報告を開き、確認済みにする | 確認待ち一覧から外れ、確認済み一覧に移る |
| P10 | 対象外（再訪問結果を段階2で採用した場合に確認） | — |
| P11 | 終了日時を過ぎた未提出案件、提出済み案件、終了前の未提出案件を見比べる | 終了日時を過ぎた未提出案件だけが未報告に出る |
| P12 | 幅390px程度とiPhone Safari実機で日程・担当変更、報告確認、写真追加・提出を試す | 操作に必要な横スクロールがなく、両役割で操作を完遂できる |
| P13 | 非対応画像、容量超過、保存失敗をそれぞれ発生させる | 各ケースで理由が表示される。保存・提出に失敗した操作は成功表示や状態更新を行わない |
| P14 | データを変更し、リセットの確認画面で実行する | 変更が消え、初期サンプルに戻る |

- P12はPC表示、幅390px程度、iPhone Safari実機を個別に記録する。AIが実機を操作できない場合は⑧で依頼者が確認する。写真選択・撮影、保存・再読込、ソフトキーボードと画面下部の操作も実機で確認する。
- ⑦では、依頼者が再現できる起動・アクセス・初期化方法、動作確認済みの版、検証結果と未確認事項を揃える。各確認は対象版、操作、期待結果、実際の結果、環境・証拠を記録する。結果は合格／不合格／未実施／対象外とし、未実施と対象外には理由を添える。[開発フロー](../development-workflow.md)

### 確定事項・仮置き・設計に渡す事項

- 既存方針に沿い、一つのWebアプリで両役割を扱い、写真を含むデータをIndexedDBに保存する。構成はTypeScript・React・Vite、shadcn/ui＋Tailwind CSS、Storybook。日時の表示・判定は日本時間。[技術構成](../prototype-handoff.md#9-技術保存についての引継ぎ)・[共通仕様](../specs/overview.md)
- サンプルは社長1名・作業員4名、元請け2社、約6件、初期の工事枠は2時間、日付は初回起動日を基準にした相対日付を仮置きとする。未割当、予定済み、未報告、確認待ち、確認済みを用意する。対象画像はJPEG／PNG／WebPで、1枚10MB・機器ごと10枚は容量と枚数の目安。件数・制限値・ケースの配置は②で具体化する。[初期設定](../prototype-handoff.md#2-確定事項仮置き未確認事項)・[保存・復元](../specs/storage.md)
- ①のP03は未提出の割当済み案件で確認する。提出後の日程・担当変更は、未提出の間に日程調整を行う案を②で推奨する。提出後も変更可能とする案では、提出した作業員と現在の担当をどう表示するかなど、報告と割当の整合を設計する必要がある。両案は②の設計確認に提示する。[予定・割当](../specs/scheduling.md)・[案件確認・報告](../specs/reporting.md)
- 実業務の人数・件数、移動や休みを考慮した割当、元請け別の写真・報告指定、現場での画像形式や通信環境は未確認。後続の利用者検証で、実際に不足した情報や手順と併せて確認する。[後続の確認事項](../prototype-handoff.md#12-優先して確認する前提後続事項)
- 適用する採用済み個別ADRはない。②でアプリ構成、保存と役割切替、デザイン管理、テスト戦略のうち記録が必要な判断をADR案にする。[ADR一覧](../adr/README.md)

## 開発計画

家庭用エアコン入替工事を題材に、サンプル案件の日時・担当を決め、作業員が現場情報を見て写真報告を提出し、管理者が報告を確認するまでを一つのWebアプリで試せるようにする。H01（割当・変更）、H02（現場での写真報告）、H03（未報告と確認待ちの区別）の操作課題をこの流れに対応づける。範囲は[引継ぎ資料の段階0〜1](../prototype-handoff.md#3-プロトタイプの範囲)に従い、開発期間・期限は設定しない。

初回の対象外は、新規案件登録、複数台報告、差し戻し・再訪問、実認証、端末間同期、LINE連携、本番インフラなど。

### 工程と次へ進む条件

| 順序 | 主な作業と成果物 | 次へ進む条件 |
| --- | --- | --- |
| 段階0・① 作業定義 | 計画を基に、初回の対象・対象外、操作と期待結果で表した完成条件、仮置き、機能の分割を作業記録にまとめる | 依頼者が目的・範囲・完成条件を確認し、対象版の承認を記録する |
| 段階0・② 設計 | 画面・導線、日時や状態のルール、保存・失敗時の振る舞い、検証方針を整理する。最小環境で「予定・割当」「作業・報告」の代表画面を用意し、後述のADR候補を具体化する | 依頼者が業務ルール・操作・代表画面を確認し、①とは別に対象版の承認を記録する |
| 段階1・③〜⑥ 機能実装・検証 | 下表の順に進める。各機能のテスト準備、実装、保存連携、画面確認、レビュー・修正を行い、最後に両役割をまたぐ通し操作を検証する | 適用するP番号の結果と実施分の証拠を記録し、⑥のレビューで見つかった修正必須事項を解消する |

### 機能の分割と依存関係

| 作業単位 | 前提 | 完了の目安と対応する確認 |
| --- | --- | --- |
| アプリ・保存の基盤 | ②設計承認。②の代表画面に必要な最小環境は設計中に準備 | 実アプリと共通部品を表示するStorybookを起動できる。架空データ、疑似役割切替、IndexedDBの初期化・保存・リセットを用意する。P13の保存失敗、P14 |
| 予定・割当 | アプリ・保存の基盤 | 管理者が架空案件に日時・担当を設定・変更し、同じ担当の重複を検知できる。P01〜P03 |
| 案件確認 | 基盤の役割切替と予定・割当 | 作業員が担当する今日の案件と現場情報を開ける。割当変更が作業員側にも反映される。P03・P04 |
| 写真・下書き | 案件確認と基盤の保存 | 写真とメモを保存し、再読込で復元できる。非対応画像・容量超過・保存失敗を操作時に確認できる。P05・P13 |
| 報告提出 | 写真・下書き | 1台分の必須写真不足を表示し、要件を満たす報告の提出を工事・報告の状態に反映する。P06の1台版・P07 |
| 管理者の報告確認 | 予定・割当と報告提出 | 未報告と確認待ちを区別し、報告を閲覧して確認済みにできる。P07・P09・P11 |
| 全体の統合確認 | 上記の動作 | 割当・変更から報告確認までを同一ブラウザで通す。再読込、保存失敗、初期化、PC・スマホでの操作を確認する。全適用項目、特にP12 |

全体の①・②をそれぞれ確認し、機能ごとの③〜⑥はAIが進める。目的・範囲・完成条件または主要な業務ルール・導線に判断が必要になった場合は、[開発フロー第9節](../development-workflow.md#9-途中で人間に判断を戻す条件)を適用する。

### 検証の進め方

- 段階1ではP01〜P05、P07、P09、P11〜P14とP06の1台版を確認する。P06の複数台版、P08、P10は段階1の対象外。複数台・差し戻し・再訪問を段階2で採用した場合に適用する。[完成条件・確認シナリオ](../specs/acceptance.md)
- 業務ルールはテストを先に書き、想定した理由での失敗と実装後の成功を確認する。特に重複の境界、写真付き下書きの復元、提出・確認後の状態整合、保存失敗時の表示を優先し、P13の各異常系は個別に記録する。
- Storybookでは共通部品の状態を確認し、実アプリではPC表示・幅390px程度の操作・iPhone Safari実機を個別に記録する。iPhoneでは写真の選択・撮影、保存と再読込、ソフトキーボードと画面下部の操作も確認する。AIが実機を操作できない場合は⑧で依頼者が確認し、確認まではP12の実機分を未実施とする。[デザイン方針](../design-guidelines.md)
- ⑥は実装時の自己確認から独立したレビューとして別セッションで行う。利用できない場合は自己レビューと記し、独立レビュー未実施を⑦の資料に残す。最終レビュー資料には型確認、静的チェック、テスト、アプリとStorybookのビルド、ブラウザ操作の結果を含める。

### 設計で具体化する事項

- 既存方針はTypeScript・React・Vite、shadcn/ui＋Tailwind CSS、Storybook、IndexedDB、架空データと疑似役割切替。採用済みの個別ADRは現時点でなく、アプリ構成、保存と役割切替、デザイン管理、テスト戦略をADR候補とする。[引継ぎ資料](../prototype-handoff.md#9-技術保存についての引継ぎ)・[ADR一覧](../adr/README.md)
