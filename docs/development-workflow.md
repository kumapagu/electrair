# electrair プロトタイプ開発フロー

- 作成日 2026年11月18日（日本時間）
- 更新日 2026年11月20日（日本時間）
- 版 1.3／テストの人間確認・独立レビュー版
- 対象 家庭用エアコン入替工事の社内業務アプリ

## 1. 目的と適用範囲

AIが設計案の作成、テスト、実装、レビュー、修正を担当し、人間が目的・方向性・テストの期待結果・最終結果を判断するための運用を定める。プロトタイプでも、①作業の定義と②設計の人間確認は別々に行い、まとめて承認しない。

業務の目的・対象範囲・技術構成は[実装引継ぎ資料](prototype-handoff.md)に従う。本資料は開発工程と確認方法の基準とし、業務仕様を重複して管理しない。版1.3は今後の開発に適用する。初回プロトタイプの確認と承認は当時の作業記録に残す。開発期間・期限は設定しない。

## 2. 全体の工程と責任

| 工程 | AIが行うこと・成果物 | 人間の確認 | 次へ進む条件 |
| --- | --- | --- | --- |
| ① 作業の定義 | 目的、範囲、対象外、完成条件、仮置き、作業分割案を整理 | 必須。何を作り、何をもって完成とするかを確認 | 人間が作業定義を承認 |
| ② 設計 | 業務ルール、状態遷移、データ、画面遷移、代表画面、検証方針を準備 | 必須。業務ルールと画面・操作の方向性を確認 | 人間が設計を承認。①の確認とは分ける |
| ③ テスト・確認項目の準備 | テストコードと操作シナリオを用意し、期待結果と実装前の失敗理由を提示 | 必須。期待結果の妥当性と必要な検証ケースを確認 | 人間がテスト内容を承認 |
| ④ 実装・検証 | ロジックとUIを実装し、テストと実画面の確認を実施 | 通常不要 | 対象のテストが通り、UIの合格条件を満たす |
| ⑤ 統合確認 | 役割・画面をまたぐ操作、保存、状態の連動を検証 | 通常不要 | 割当から報告確認までの流れがつながる |
| ⑥ AIレビュー・修正 | 4観点の独立レビューを行い、修正・再検証 | 仕様変更等の判断がある場合のみ | 修正必須の指摘が解消している |
| ⑦ 最終レビューの準備 | 動くアプリ、確認手順、検証結果、仮置き・制限・未確認事項を整理 | 通常不要 | 人間が操作して採否を判断できる |
| ⑧ 人間の最終レビュー | AIは確認を支援し、指摘に対応 | 必須。業務適合、操作性、表示・用語、採否を判断 | 採用、修正、保留と理由を記録 |

①の承認後に②へ進む。②では設計確認に必要な最小の環境やサンプル画面を作ってよい。②の承認後に③へ進み、③でテスト内容を承認してから本格的な機能実装を始める。③〜⑥は機能単位で繰り返し、⑤で全体の流れも確認した後に⑦・⑧へ進む。

## 3. ① 作業の定義と人間確認

### AIが用意するもの

- 解決したい課題と、今回確かめる仮説。
- 今回作る範囲と作らない範囲。
- 利用者、利用端末、前提条件。
- 操作と期待結果で表した完成条件。[確認シナリオ](specs/acceptance.md)のP01〜P14と対応づける。
- 確定事項、仮置き、未確認事項と、判断が必要な点への推奨案。
- 機能単位の作業分割案。日数による期限は置かない。
- 既存ADRの適用状況と、今回新しく判断が必要な事項。

人間は「この課題と範囲で進めてよいか」「完成条件が目的に合っているか」を確認する。内部構造や詳細なテストコードの確認は求めない。指摘はAIが作業定義に反映し、承認した版を記録してから②へ進む。

既存資料で決定済みの事項は再利用する。資料が存在するだけで今回の作業定義が承認済みとは扱わない。

## 4. ② 設計と人間確認

### AIが用意するもの

- 業務ルールと状態遷移、保存・提出・確認の意味。
- 画面一覧、画面遷移、主要操作、入力不足や保存失敗時の振る舞い。
- サンプルデータで操作できる代表画面「予定・割当」「作業・報告」。
- データ・処理・共通部品の構成、テストとブラウザ確認の分担。
- 人間が判断する点、仮置き、制限。技術的な詳細は補足にまとめる。
- 重要な設計判断のADR案。人間の判断が必要なものは設計確認に含める。

代表画面はiPhoneを優先した表示で用意し、PC表示も確認する。この段階ではサンプルデータや仮の処理を使用してよい。未接続の保存処理や仮の操作があれば明示し、機能の動作検証が終わったとは扱わない。

人間は、必要な情報があるか、操作の順序が自然か、業務ルールが合っているか、文字・ボタン・状態表示が分かりやすいかを確認する。内部の実装方式・部品構成・テスト設計は原則AIが判断する。

指摘はAIが設計と代表画面に反映し、設計承認を別途記録する。①で承認した目的・範囲・完成条件を変える場合は、変更点を明示して①の該当部分を再確認してから設計を確定する。

## 5. ロジックの開発とテスト

仕様・合格条件 → テスト作成 → 想定した理由で失敗することを確認 → ③で人間がテスト内容を確認・承認 → ④実装 → テスト成功 → コード整理 → 再確認、の順で進める。実行環境が壊れているための失敗を、仕様を検証するテストの失敗として扱わない。

| 対象 | 主な確認例 |
| --- | --- |
| 予定の重複 | 同じ担当の時間重複は保存不可。終了と次の開始が同時刻なら重複しない |
| 日時の入力 | 終了が開始以前の場合は保存不可 |
| 報告提出 | 施工前・施工後の写真が各1枚以上必要。任意項目の不足で提出を止めない |
| 下書き | 提出条件を満たさなくても保存可能。再読込後に写真・入力を復元 |
| 状態遷移 | 提出後は確認待ち・編集不可。確認待ちから確認済みへ変更できる |
| 保存失敗 | 失敗を通知し、保存成功や提出成功を表示しない |

業務ルールは単体テスト、入力やイベントの連動は部品テスト、保存の連携は結合テスト、一連の操作はブラウザで確認する。主要な操作シナリオは必要な範囲でE2Eテストにする。テストを増やすこと自体を目的にせず、合意した振る舞いと不具合のリスクに応じて選ぶ。

### ③ テスト内容の人間確認

AIは、完成条件ID、操作・前提、期待結果、対応するテストファイルとケース名、実装前に想定した失敗理由と結果を揃える。正常系、異常系、境界条件を含め、ブラウザなどで確認する項目はその方法も記す。人間は機能単位で、期待結果が業務に合うか、検証すべきケースが抜けていないかを確認する。対応するテストコードを参照できる形にし、必要な箇所を一緒に確認する。

対象版、確認した範囲、判断、確認日、判断者、根拠を作業記録に残す。承認後に該当する実装を開始する。合意した期待結果に影響する変更や重要な検証ケースの追加が必要な場合は③の該当部分を再確認する。目的・範囲・完成条件や主要な業務ルールの変更は第9節に従う。期待結果や検証範囲を変えないテストの整理はAIが行う。

テスト成功は必要条件であり、完成の十分条件にはしない。レビューではテスト自体が仕様と対応しているかも確認する。通すためだけに期待値を変えず、仕様変更が必要なら理由を記録し、第9節の判断ルールに従う。カバレッジ率だけで完成を判断しない。

## 6. UIの開発と確認

操作設計 → 状態別の確認項目 → UI実装 → Storybook・ブラウザで確認 → 修正、の順で進める。入力制御など期待する振る舞いが明確な部分はテスト先行にする。見た目と操作性は実画面でも確認する。

| 観点 | 合格条件の例 | 確認方法 |
| --- | --- | --- |
| 機能 | 入力・選択・保存・エラー表示が仕様どおり | 自動テストとブラウザ操作 |
| 表示 | 文字切れ・重なり・操作に必要な横スクロールがなく、共通ルールに沿う | 代表幅の画面と画像の目視確認 |
| 操作性 | 次の操作と結果が分かり、誤操作から戻れる。ドラッグを必須にしない | 実アプリの操作シナリオ |
| アクセシビリティ | ラベル、フォーカス、キー操作、色以外の状態表示を確認 | 自動チェックと操作確認 |
| 端末 | 管理・報告ともスマホで完結し、PCでも利用可能 | PC、スマホ幅、iPhone Safariを区別して記録 |

変更に関係する通常・空状態・入力エラー・処理中・保存失敗・操作不可の状態を用意する。写真追加欄では、写真なし、追加・削除、処理中、非対応形式、容量超過、保存失敗、必須写真不足を確認する。存在しない状態を網羅目的で追加しない。

Storybookでは実アプリと同じ共通部品の状態を確認する。実アプリでは画面遷移・業務の流れ・保存を確認する。初期対象はボタン、入力欄、状態ラベル、案件カード、写真追加欄。全画面登録や網羅的な画像比較テストを初回の完成条件にはしない。代表画面の画像を変更確認に使い、安定した部品から必要に応じて画像比較を自動化する。

iPhone実機では、写真選択・撮影、ソフトキーボード、画面下部の操作、保存・再読込を確認する。AIが実機を操作できない場合は⑧で人間が確認する。PCでの表示幅変更や別ブラウザによる確認を、iPhone Safari実機確認と記録しない。実機未確認の項目は未確認のまま提示し、必要な確認が済むまで実機の完成条件を達成したと扱わない。

## 7. 機能単位の実装と統合確認

| 単位 | 動く状態として仕上げる範囲 |
| --- | --- |
| ① 予定・割当 | 未割当案件の日時・担当設定、変更、重複検知 |
| ② 案件確認 | 作業員が自分の案件と現場情報を確認 |
| ③ 写真・下書き | 写真・メモの保存と再読込後の復元 |
| ④ 報告提出 | 不足の表示、提出、管理者の確認待ちへの反映 |
| ⑤ 管理者確認 | 報告閲覧、確認済みへの変更 |

全体の作業定義・設計を人間が承認した後、各単位の③の確認資料をAIが用意する。人間がテスト内容を承認した単位からAIが④〜⑥を進める。初期設定・サンプル・保存の基盤、リセット等も必要な作業として計画に含める。

統合確認では、未割当案件の割当 → 作業員の案件確認 → 写真・下書き → 提出 → 管理者の報告確認を試す。日時・担当変更の反映、再読込、未報告と確認待ちの区別、エラー時に成功扱いにならないことも確認する。同一ブラウザの役割切替による検証であり、複数端末同期や実認証を検証したとは扱わない。

## 8. AIレビューと修正

実装中の自己確認と分け、4人のレビュワーエージェントに1観点ずつ割り当て、独立したセッションで並行レビューする。同時実行数に制限がある場合は、担当を分けたまま複数回に分けて実施する。

レビュワーは全員 `gpt-6.2-sol` を使用する。起動時の指定は[レビュー手順](../.agents/skills/review-task/SKILL.md)を参照する。

エージェントレビューは⑥で実施する。PRを作成する場合は、PR上でのエージェントレビューを省き、⑥のレビュー対象コミット・比較元・結果と作業記録へのリンクをPR本文に記載する。レビュー後に差分が変わった場合は、該当のレビュワーが⑥で変更箇所と影響範囲を再確認し、その結果をPRに反映する。

| 担当 | 主な確認事項 |
| --- | --- |
| 開発ルール・工程 | 承認範囲、リポジトリのルール、作業記録・承認済み仕様・ADR・実施結果の整合 |
| セキュリティ・データ保護 | 入力・写真の検証、データの閲覧範囲、意図しない外部送信、保存・初期化時のデータ消失 |
| 仕様・実装 | 承認済み仕様と実画面・処理の一致、状態の整合、連続操作・再読込、アクセシビリティ、対象範囲 |
| テストの網羅性 | ③で合意した期待結果とテストコードを照合し、正常・異常・境界条件の抜けや、不具合を見逃す検証を特定する。必要に応じ自動テスト・手動確認の両方を確認する |

各レビュワーには、担当観点、共通の対象コミットと比較元、承認済み仕様・作業記録・ADR、テスト・検証結果の参照先だけを渡す。実装セッションの会話履歴、推論、実装者の所見を引き継がない。初回レビューは他のレビュワーの指摘を共有せずに行い、担当AIが提出後に照合・集約する。各指摘には根拠、対象箇所、再現条件、影響を添える。テストの指摘では対応する仕様、抜けているケース、見逃しうる不具合を明記する。

独立セッションを使えない場合は、該当の観点を自己レビューまたは未実施として理由とともに記録し、⑦に引き継ぐ。

指摘は「修正必須」「改善候補」「要判断」に分ける。操作不能、データ消失、誤った成功表示、完成条件への違反などは修正必須とし、解消してから⑦へ進む。改善候補は記録して後続へ回せる。要判断は推奨案と影響を添えて人間に提示する。

修正後は該当テストと影響範囲を再検証し、修正必須の指摘は該当レビュワーへ再確認を依頼する。共通部品・保存・状態遷移に影響する変更は関連機能も確認する。完了時には型確認、設定した静的チェック、対象の自動テスト、アプリとStorybookのビルド、主要な操作シナリオの結果を整理する。問題なく確認済みの項目を理由なく繰り返さない。

## 9. 途中で人間に判断を戻す条件

| 変更・問題 | 扱い |
| --- | --- |
| 目的、対象範囲、完成条件を変える | ①の該当部分を再確認。その後、必要な設計を更新 |
| 必須入力、操作手順、主要な業務ルール・画面導線を変える | ②の該当部分を再確認。①にも影響すれば①から見直す |
| 決定事項が矛盾し、選択によって大きな作り直しになる | 選択肢・推奨案・影響を提示して判断を求める |
| 承認した仕様どおりに動かすための不具合修正 | AIが進め、再検証して記録 |
| 軽微な文言・余白調整、内部構造の整理 | 意味や操作を変えない範囲でAIが判断 |
| 新機能や初回対象外の改善提案 | 後続候補として記録。勝手に実装範囲へ加えない |

判断を求める前に、AIが確認資料、選択肢、推奨案、変更の影響を揃える。判断待ちの変更は進めず、依存しない承認済み作業は継続できる。軽微な仮置きは記録して進め、人間の確認を細分化しすぎない。

## 10. 最終レビューと完了の扱い

AIは以下をまとめて提示する。

- 動くアプリの版、起動・アクセス方法、初期データへの戻し方。
- 割当から報告確認までの操作シナリオと期待結果。
- 今回の実装範囲、主な変更点。
- テスト・ブラウザ操作・表示確認の結果、端末とブラウザ。
- 仮置き、改善候補、制限、未確認事項、必要な実機確認。
- 今回追加・変更したADRと、採用した理由・受け入れた制限。

人間は管理者・従業員の両役割で操作し、業務への適合、操作の分かりやすさ、表示・用語、実機の動作を確認する。コードや全テストを読み直すことは求めない。

修正指摘があればAIが対応し、⑥・⑦を経て変更箇所と影響範囲を再提示する。仕様変更なら第9節に従う。「採用」「修正」「保留」を対象の版・範囲・理由とともに記録する。未確認の完成条件があれば、次の扱いと担当を明記し、すべて確認済みとは記録しない。

本人の最終確認と修正の後に、実際の社長・従業員による検証を行う。本人の承認や自動テスト成功だけで、実利用者への有効性や業務負担の削減が確認できたとは扱わない。

## 11. 作業記録の最小テンプレート

作業ごとに以下を一つの記録にまとめる。確認結果の状態は「合格／不合格／未実施／対象外」を使い、未実施と対象外には理由を添える。

| 項目 | 記入内容 |
| --- | --- |
| 作業ID・対象の版 | 対象機能と確認する成果物の版 |
| 作業定義 | 目的、範囲、対象外、完成条件、仮置き |
| ① 人間確認 | 対象版、承認・修正・保留、確認日、判断者、理由 |
| 設計 | ルール、状態遷移、代表画面、検証方針への参照 |
| 関連ADR | 適用・追加・置換したADRへの参照、判断者と判断状況 |
| ② 人間確認 | 対象版、承認・修正・保留、確認日、判断者、理由 |
| ③ 人間確認 | 対象版、検証ケースと期待結果、対応するテスト、想定失敗の結果、承認・修正・保留、確認日、判断者、根拠 |
| 確認結果 | 完成条件ID、方法・実行手順、期待結果、実際の結果、環境、証拠 |
| AIレビュー | 指摘、重要度、修正内容、再検証結果、残る改善候補 |
| ⑧ 最終レビュー | 対象版、採用・修正・保留、確認日、判断者、理由 |
| 次の扱い | 未確認事項、後続候補、担当、再確認する条件 |

①・②・③の確認記録と⑧の採否判断は分ける。承認のないまま次工程へ進めず、今回のフロー合意を個別作業の承認として流用しない。

## 12. ADRの運用

### 目的と記録する判断

ADR（Architecture Decision Record）は、重要な設計・技術の選択について「なぜ選んだか」を残す記録とする。AIが起案・更新し、必要な人間の判断を既存の①・②・⑧の確認に組み込む。ADR専用の定例や一律の承認工程は設けない。

後から変更すると影響が大きい判断、または将来その理由を知る必要がある判断を記録する。

| ADRに残すもの | 通常は別の記録で管理するもの |
| --- | --- |
| アプリ構成、主要技術の選定 | 関数名・ファイル名などの細かな実装判断 |
| 保存・認証・同期の方式と制約 | 個別の入力項目や業務仕様 |
| 状態管理、機能間の責務分担 | 仕様どおりに直す不具合修正 |
| デザイン管理、共通部品の方針 | 軽微な余白・文言調整 |
| テスト戦略、重要な検証方法 | テスト実行結果、作業進捗 |
| 重要な制約を受け入れる判断 | 重要な選択を伴わない作業記録 |

例えば、同一ブラウザ内保存を採用して端末間共有を今回行わない判断は、理由・制限・見直す条件をADRに残す。施工前後の必須写真枚数は業務仕様として管理し、それに伴う重要な技術判断がある場合にADRから参照する。仕様本文やテスト結果をADRへ重複転記しない。

### 開発工程への組み込み

| 工程 | ADRの扱い |
| --- | --- |
| ① 作業の定義 | 既存ADRを読み、適用する決定と新たな判断事項を洗い出す |
| ② 設計 | AIが背景・選択肢・推奨案・影響をADR案にまとめ、必要な人間確認を設計確認に含める |
| ③〜⑤ テスト・実装・統合確認 | 採用済みADRに従う。新しい重要判断を記録し、判断権限に応じて決定する |
| ⑥ AIレビュー | ADRと実装の整合、判断の記録漏れ、未決定事項を確認する |
| ⑦ 最終レビュー準備 | 今回追加・変更したADRと、理由・制限・見直す条件をまとめる |
| ⑧ 最終レビュー | 実装結果と判断の影響を確認する。決定を変える場合は置換ADRを作る |

ADRの作成要否と、人間の承認要否は別々に判断する。目的・範囲・完成条件への変更は①へ、必須入力・主要な操作・業務ルール・設計の方向性への変更は②へ戻す。既存決定との矛盾を含め、第9節の条件に該当する判断はAIだけで確定しない。

承認済みの範囲内で人間確認が不要な技術判断は、AIが理由を記録して採用し、⑥でレビューする。人間確認が必要なADRは承認まで「提案中」とし、それに依存する実装を先行しない。後の最終レビューを、必要な事前確認の代用にしない。

### 保管場所と番号

コードと同じプロジェクト内のMarkdownで管理する。一覧とテンプレートは整備済み。個別ADRの作成や採用は未実施。

| 配置 | 内容 |
| --- | --- |
| `docs/adr/README.md` | 本節への参照と、番号・タイトル・状態・置換先を示す一覧 |
| `docs/adr/template.md` | ADRの共通テンプレート |
| `docs/adr/0001-xxxx.md` | 1件の重要な決定 |

番号は4桁の連番とし、既存番号を再利用・振り直ししない。1件につき一つの判断を基本とする。コードに伴う新しい決定は、可能な限り実装と同じ変更・レビューに含める。PRを利用しない場合も変更記録から関連ADRを参照できるようにする。

### 共通テンプレート

```markdown
# ADR-XXXX: 決定のタイトル

- 状態: 提案中
- 日付: YYYY-MM-DD
- 判断者: 未決定
- 関連: 仕様・設計・関連ADRへのリンク
- 置換関係: なし（該当時は置換元・置換先のADRを記載）

## 背景
何が課題か。今回の制約は何か。

## 比較した選択肢
候補と、それぞれの利点・欠点。

## 決定
提案中は推奨案、採用後は確定した決定を記載する。

## 理由
今回、この選択が適切な理由。

## 影響と受け入れる制限
得られること、負担、できないこと。

## 見直す条件
どのような状況になったら再検討するか。
```

人間が判断した場合は確認日・判断者と①または②の承認記録を関連づける。AIが決定した場合もその旨を明記し、人間が承認したと誤認させない。提案中のADRには推奨案と判断が必要な点を示す。

### 状態と変更履歴

| 状態 | 意味 |
| --- | --- |
| 提案中 | 比較・確認中。まだ採用していない |
| 採用 | 現在有効な決定 |
| 不採用 | 検討したが採用しなかった。理由を残す |
| 置換済み | 新しい採用済みADRに置き換えられた |

採用済みADRの背景や決定を、当時の判断が消える形で書き換えない。誤字修正・意味を変えない補足・状態と置換先の更新は行ってよい。判断を変更する場合は新しいADRを作り、新ADRの採用時に旧ADRを「置換済み」にして相互リンクを残す。新ADRが提案中の間は旧ADRを有効な決定として扱う。

プロトタイプでは特に見直す条件を残す。例えばブラウザ内保存なら「複数端末で共有する段階へ進むときに再検討」とし、試作用の選択を本番へ無条件で継続しない。

### 初期ADRの候補と事後記録

最初の候補は、技術・アプリ構成、保存と疑似的な役割切替、デザイン管理、テスト戦略とする。実際の分割は判断のまとまりに合わせ、関連の薄い決定を一件に詰め込まない。

既存方針を記録するときは「既存方針の事後記録」と明記し、根拠となる資料と記録日を示す。決定日が不明なら不明とし、当時比較していない選択肢や確認できない採用理由は作らない。新たな比較・考察を加える場合は事後の評価と区別する。既存の決定か新しい提案かを区別し、未承認の方針を採用済みとして記録しない。
