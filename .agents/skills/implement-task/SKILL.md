# implement-task

プロジェクトルートを基準にパスを解決し、AGENTS.md、docs/development-workflow.md、docs/tasks/README.md、対象作業記録を読む。手順から仕様や承認を新設・上書きしない。結果は対象作業記録へ残す。

## 手順

1. ①・②の承認と、親作業から適用される範囲を確認する。未承認の依存作業を始めない。
2. 対象仕様・採用済みADR・関連コードを読み、今回のP番号と正常・異常・境界条件を選ぶ。新機能を増やさない。
3. 実行環境・既存コマンドを確認する。環境構築が対象ならバージョンと起動・検証・スマホアクセス方法をdocs/README.mdに記録する。
4. ロジックのテストを先に作り、想定した理由で失敗することを確認する。環境故障を仕様の失敗扱いしない。
5. ③で完成条件ID、前提・操作、期待結果、対応するテストのケース名・参照先、想定した失敗理由・結果を提示する。機能単位の人間確認を対象版・範囲・日付・判断者・根拠付きで記録し、承認された単位から④へ進む。
6. 実装し、テスト成功後に構造を整理して再確認する。合意した期待結果に影響する変更や重要な検証ケースの追加は③へ、仕様変更は開発フロー第9節の該当工程へ戻す。
7. UIの必要な状態を用意し、実アプリと共通部品のStorybookを確認する。画像・操作の確認をテスト結果で代替しない。
8. 保存失敗、再読込、役割間の状態連動を確認する。機能単位と全体の割当→報告→確認の流れを確認する。
9. 型・静的チェック、対象テスト、アプリ・Storybookのビルド等を変更に応じて実行する。未整備・実行不能は理由付き未実施とする。
10. 変更と検証結果・対象コミット・比較元、③の確認資料への参照を記録して⑥へ渡す。

成果物は③の確認資料・承認記録、変更、必要なテスト・Story、実行結果、レビュー対象の版とする。
